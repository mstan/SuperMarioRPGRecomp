# Contributing

Thank you for helping improve the Super Mario RPG SNES recomp. The project
keeps ROM data and generated game code out of Git, so a working checkout has
two explicit inputs: the pinned `snesrecomp` and `recomp-ui` submodules, and
your own legally obtained ROM.

## Set up a checkout

```bash
git clone --recurse-submodules git@github.com:mstan/SuperMarioRPGRecomp.git
cd SuperMarioRPGRecomp
git submodule update --init --recursive
```

Stage a verified US ROM as `smrpg.sfc` at the repository root and generate
the private C sources:

```bash
bash tools/regen.sh
```

`tools/regen.sh` verifies the ROM's SHA-256 before doing anything else, so a
mismatched or wrong-region ROM fails loudly instead of generating garbage.
The ROM and `src/gen/` are ignored and must never be committed. See the
README for the expected ROM hash.

## Build and test

For a development build:

```bash
cmake -S . -B build-dev -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-dev --target SuperMarioRPGSNESRecomp
```

There is no test suite wired into CTest for this game yet; validate changes
with the headless host instead:

```bash
cmake --build build-dev --target SuperMarioRPGSNESRecompHeadless
./build-dev/SuperMarioRPGSNESRecompHeadless smrpg.sfc 36000
```

It exits nonzero on a runtime failure or a failed attract-soak qualification
threshold (see the README's [Qualification](README.md#qualification)
section for what "qualified" means). Re-run it after any change that could
affect frame timing, SA-1 execution, or PPU/APU output, and re-run the
public-disassembly ingest (`tools/ingest_smrpg_disassembly.py`) only if you
touch that tool itself — it does not need to run for ordinary changes.

On Windows, generate sources from Git Bash (MSYS2), then build with CMake +
Ninja + the mingw64 toolchain (`cmake -S . -B build-dev -G Ninja ...`). There
is no Visual Studio solution for this game.

## Change the framework dependency

The `snesrecomp` and `recomp-ui` gitlinks are the single source of truth for
the framework and launcher-UI revisions. Normal game-only changes should
leave them untouched.

For coordinated framework work, create a branch inside the submodule, commit
and push that change first, then stage the new gitlink in this repository:

```bash
git -C snesrecomp switch -c your-branch
# edit, test, commit, and push snesrecomp
git add snesrecomp
git diff --cached --submodule=log -- snesrecomp
```

Both submodules are junctioned to the same shared tree used by every other
game in this family (Mega Man X, Mega Man X2/X3, Zelda, Super Mario Kart)
when developed locally — a framework fix made here is expected to be
regenerated and re-tested against those titles too, not just this one, since
`v2_emit.py` / `recomp.py` changes are shared code. Do not submit a
game-repository gitlink until the referenced framework commit is reachable
from the configured submodule remote.

## Regenerating generated code (`src/gen/`, `recomp/funcs.h`)

Never hand-edit `src/gen/*.c` or `recomp/funcs.h` — both are fully
regenerated by `tools/regen.sh` from `recomp/bank*.cfg` and the ROM, and any
manual edit is silently discarded on the next regen. If generated output is
wrong, the fix belongs in the recompiler (`snesrecomp/recompiler*/`) or in
`recomp/bank*.cfg`'s declarations/hints, not in the generated C itself.

`recomp/tier2_coverage.json` is the one generated-looking file that IS
meant to be committed: it's the coverage/qualification manifest that
`tools/regen.sh` feeds back into the analyzer to promote interpreter
discoveries to AOT roots. Update it with
`python tools/merge_tier2_coverage.py recomp/tier2_coverage.json <captures...>`
after a headless soak that observes new coverage, not by hand.

## Before opening a pull request

- Confirm `git submodule status --recursive` has no `-`, `+`, or `U` prefix.
- Build `SuperMarioRPGSNESRecomp` and `SuperMarioRPGSNESRecompHeadless`, and
  run a headless soak (`SuperMarioRPGSNESRecompHeadless smrpg.sfc 36000`) to
  confirm it still qualifies.
- Run `git diff --check` and inspect `git status --short` for ROMs,
  generated sources, build trees, saves, or unrelated files.
- Describe which platforms were exercised and whether validation was
  automated (headless soak / TCP capture) or a human playthrough. This
  project does not yet have a confirmed human playthrough — say so plainly
  if yours doesn't change that.
